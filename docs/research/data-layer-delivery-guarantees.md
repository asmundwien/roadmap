# Data-layer delivery guarantees

Research for [What do HTTP and WebSocket guarantee about authority and uncertain command delivery?](https://github.com/asmundwien/roadmap/issues/105), under [Rework Roadmap's data layer with clearer models and less code](https://github.com/asmundwien/roadmap/issues/102).

Source baseline: [`7e70e8975b59aa1b435d444cd9c7ba06c886f8a4`](https://github.com/asmundwien/roadmap/tree/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4). Sources accessed 2026-10-08. This report establishes transport facts and their limits. It chooses no application design, handshake, retry, timeout, heartbeat, library, or state owner and resolves no HITL decision.

## Versions and evidence boundary

- WHATWG [Fetch](https://fetch.spec.whatwg.org/commit-snapshots/e9460d1b22ead1c6a72eeac37fb2ec0dc01aeb1d/) revision `e9460d1b22ead1c6a72eeac37fb2ec0dc01aeb1d`, last updated 2026-10-06, and [WebSockets](https://websockets.spec.whatwg.org/commit-snapshots/9879e5cf0d66c66af6990e4c75f72dda794e1b87/) revision `9879e5cf0d66c66af6990e4c75f72dda794e1b87`, last updated 2026-03-15. These are specification requirements, not measurements of an identified browser build.
- [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html), December 2011, defines the WebSocket protocol. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) and [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html), June 2022, define HTTP semantics and HTTP/1.1 connection ordering.
- Node [HTTP](https://nodejs.org/download/release/v26.8.1/docs/api/http.html) and [streams](https://nodejs.org/download/release/v26.8.1/docs/api/stream.html) documentation is pinned to v26.8.1, the runtime named in the [architecture review baseline](https://github.com/asmundwien/roadmap/issues/102#issuecomment-6054933978). The root [package manifest](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/package.json#L8-L10) permits Node `>=22.22.0`; this research did not inspect a running deployment. The server's `@types/node` range `^24.13.3` is a development dependency, not runtime identification.
- The server [manifest](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/server/package.json#L11-L20) declares `ws ^8.21.3`; the [lockfile](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/pnpm-lock.yaml#L72-L74) resolves `8.21.3`. Library claims below use the official [ws 8.21.3 API documentation](https://github.com/websockets/ws/blob/8.21.3/doc/ws.md).

Only source and primary documents were read. No commands, runtime probes, tests, builds, lint, or formatters ran. The baseline review's reproduced behavior is attributed to that review, not a new reproduction.

## Facts and limits

"Authority" below means Roadmap's current application session, not HTTP's URI-origin authority.

| Observation or boundary | Guaranteed or documented fact | What it does not establish |
| --- | --- | --- |
| Data received on one WebSocket connection | RFC 6455 uses TCP. Message fragments must arrive in sender order, and fragments of different messages cannot interleave without a negotiated extension that permits it. Complete messages follow these framing rules; browser message events use the WebSocket task source. [RFC 6455 §§1.7, 5.4, 6.2](https://www.rfc-editor.org/rfc/rfc6455.html#section-5.4), [WHATWG feedback](https://websockets.spec.whatwg.org/#feedback-from-the-protocol). | This is connection-local order in each direction, not a total order of application operations. It does not promise that every attempted send reaches the peer or that asynchronous handlers finish in arrival order. |
| A replacement socket or an HTTP response arrives after another observation | HTTP correlates responses with requests using a version-specific mechanism. HTTP/1.1 requires responses in request order on the same connection, including pipelined requests. Multiple connections are permitted. [RFC 9110 §7.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-7.5), [RFC 9112 §§9.2, 9.3.2, 9.4](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.2). | These rules supply no order between independent sockets, or between WebSocket messages and HTTP responses. Later arrival does not mean later state capture or a newer application session. Fetch call order is not a cross-request completion-order guarantee. |
| Browser WebSocket `open` | The opening handshake has established the connection; the browser sets `OPEN` and fires `open`. Communication is possible. [WHATWG interface and feedback](https://websockets.spec.whatwg.org/#feedback-from-the-protocol). | No Roadmap baseline has necessarily been received, decoded, or accepted. `open` identifies no epoch and proves neither application synchronization nor command completion. |
| Browser WebSocket `close`, including `wasClean` | `close` reports connection closure; `wasClean` concerns protocol closure. Browser code cannot distinguish several opening failures from an abrupt post-handshake failure through detailed diagnostics. [WHATWG close feedback](https://websockets.spec.whatwg.org/#closeWebSocket), [RFC 6455 §7.1.4](https://www.rfc-editor.org/rfc/rfc6455.html#section-7.1.4). | Closure does not prove server restart, retirement of an epoch, receipt or application of a snapshot, or the outcome of a separate HTTP command. A clean close is not an application acknowledgement. |
| `fetch()` fulfills with a `Response` | Fetch resolves when its response-processing algorithm exposes a non-network-error response. HTTP error statuses do not themselves reject Fetch. Body consumption is separate, and `json()` can reject on read or parse failure. [Fetch §5.6](https://fetch.spec.whatwg.org/#dom-global-fetch), [body consumption](https://fetch.spec.whatwg.org/#concept-body-consume-body). | A fulfilled promise alone does not prove a complete readable result or business success. RFC 9110 says `200` indicates request success, but POST content describes the action's status or result; `202` explicitly leaves processing incomplete. Operation completion and durability still depend on the endpoint contract. [RFC 9110 §§15.3.1, 15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.1). |
| Fetch rejects, response reading fails, or a result cannot be decoded | A network error rejects Fetch with `TypeError`. Fetch can also return a network error after receiving an HTTP response when the CORS response check fails. Body read or JSON conversion failures reject body consumption. [Fetch §5.6](https://fetch.spec.whatwg.org/#dom-global-fetch), [HTTP fetch](https://fetch.spec.whatwg.org/#concept-http-fetch), [body consumption](https://fetch.spec.whatwg.org/#concept-body-consume-body). | Failure alone does not distinguish failure before dispatch from a lost or unreadable response after execution. It proves neither non-execution nor rollback. RFC 9110 explicitly allows communication failure after the original request succeeded. [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2). |
| Fetch signal is already aborted before the call, versus abort after dispatch | An already-aborted signal makes `fetch()` return before invoking the fetch algorithm. A later abort rejects the pending promise, cancels a readable request body, and errors a readable response body; rejecting an already-fulfilled promise is a no-op. [Fetch §5.6](https://fetch.spec.whatwg.org/#abort-fetch). | The first case establishes no dispatch by that call. A later abort supplies no server-side undo or completion acknowledgement. `AbortError` alone does not establish when abort happened, and a custom abort reason need not be `AbortError`. |
| Node `IncomingMessage` completion, closure, or interruption | `complete` means a complete HTTP message was received and parsed. Since Node 16, request `close` concerns request completion, not underlying socket closure. `aborted` is deprecated; `destroyed` can also become true after normal consumption. A prematurely destroyed request stream may emit neither `end` nor `finish`; readable streams can emit errors. [Node incoming messages](https://nodejs.org/download/release/v26.8.1/docs/api/http.html#class-httpincomingmessage), [stream completion](https://nodejs.org/download/release/v26.8.1/docs/api/stream.html#streamfinishedstream-options-callback), [readable errors](https://nodejs.org/download/release/v26.8.1/docs/api/stream.html#event-error-1). | These are HTTP parsing and stream-lifecycle facts, not command admission or execution facts. `close` or `destroyed` alone is not proof of an aborted command. A full request body is not proof that the client will receive the result. |
| Node response `finish` or `close` | `finish` means response headers/body were handed to the operating system, not received by the client. Response `close` can mean completion or premature connection termination. [Node response events](https://nodejs.org/download/release/v26.8.1/docs/api/http.html#event-finish-1). | Neither event proves client receipt, decoding, synchronization, or undo of an already-performed host effect. |
| ws `send()`, its callback, or `bufferedAmount` | The callback reports that data was written out or reports an error. `bufferedAmount` counts queued bytes not yet transmitted to the network and includes framing bytes. The optional `createWebSocketStream()` exposes Node's Duplex stream API. [ws send](https://github.com/websockets/ws/blob/8.21.3/doc/ws.md#websocketsenddata-options-callback), [buffering](https://github.com/websockets/ws/blob/8.21.3/doc/ws.md#websocketbufferedamount). | Writing out, successful return, or zero queued bytes is not a peer-application acknowledgement. Node stream backpressure uses `write()`'s boolean result and `drain`; `highWaterMark` is a threshold, not a strict memory cap. Do not attribute that boolean contract to ws `send()`. [Node buffering](https://nodejs.org/download/release/v26.8.1/docs/api/stream.html#buffering). No slow-client cost or throughput was measured here. |

## Known rejection versus unknown completion

A readable rejection can establish non-execution only when its provenance and endpoint contract establish that rejection happened before command admission. HTTP `403` means refusal to fulfill; `500` means an unexpected condition prevented fulfillment. Neither definition promises transactional rollback of every side effect. [RFC 9110 §§15.5.4, 15.6.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4).

At this baseline, [transport acceptance](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/server/src/transport.ts#L99-L144) returns before dispatch on Origin, method, loopback, or content-type rejection. [Body and command validation](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/server/src/transport.ts#L174-L188) also precede `application.execute()`. An attributable response from one of those branches proves this transport did not invoke that command. This is source-owned admission policy, not a property of every HTTP error response. Some such responses are plain errors, while the [client expects a command-result envelope](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/web/src/store/roadmap-store.ts#L152-L180); undecodability therefore does not imply that execution was possible in every failure case.

Conversely, execution precedes response-envelope validation and transmission. [Result encoding failure](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/server/src/transport.ts#L214-L226), response loss, or client read failure can leave completion unknown. A decoded outcome gives the application-defined result of that invocation, not proof of current session authority. For a [native launch](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/server/src/application/operations.ts#L75-L123), the operation awaits the host launch and returns a result without recording a state transition in this function. A later live snapshot alone cannot distinguish launch completion from non-execution.

Node's stream documentation shows [async consumption with promise error handling](https://nodejs.org/download/release/v26.8.1/docs/api/stream.html#readablesymbolasynciterator). The baseline [body reader](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/server/src/transport.ts#L277-L301) consumes `IncomingMessage` with `for await` outside its JSON parsing catch, while the [caller detaches the async handler](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/server/src/transport.ts#L73-L106). [INFERENCE] A rejected stream read can escape that handler before dispatch rather than become its typed body failure. No interruption or process-exit scenario was run here. Server knowledge that dispatch was not reached is distinct from what a browser that receives no response can know.

POST supplies no generic exactly-once or safe-repeat guarantee. RFC 9110 §9.2.2 says a client SHOULD NOT automatically retry a non-idempotent request unless it knows the operation is idempotent or can detect that the original request was never applied. This report specifies no retry policy.

## Motivating authority counterexample

The [architecture review baseline](https://github.com/asmundwien/roadmap/issues/102#issuecomment-6054933978) reports this reproduced sequence:

1. A command begins before the client has observed old server epoch A.
2. After restart, WebSocket state B/1 becomes the first accepted epoch.
3. A delayed HTTP command result A/10 arrives. The store adopts A and retires B.
4. The store then rejects B/2 and remains at A/10.

The [shared state arbiter](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/web/src/store/roadmap-store.ts#L92-L103) compares sequences only within an equal epoch. It accepts a different epoch unless previously retired; [HTTP outcomes use the same arbiter](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/web/src/store/roadmap-store.ts#L161-L163). Thus a previously unseen predecessor defeats the retired-epoch set. This is an application arbitration counterexample, not a standards-defined ordering of epochs or a violation of WebSocket's connection-local ordering. Opaque epoch inequality cannot tell the client which server session is newer.

The server [sends current state after its ws connection event](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/server/src/transport.ts#L44-L56), but the client [marks transport live on `open`](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/web/src/store/roadmap-store.ts#L110-L123). That readiness label is application policy; the standard does not turn it into proof that the baseline arrived.

## Facts the application must own

The cited protocols do not supply the following Roadmap-specific facts. Any later contract claiming them must define their meaning and evidence:

- Which application session produced an observation or command outcome, and why that session is accepted as current relative to other sessions and outstanding requests. Connection identity and opaque epoch equality alone do not establish chronological authority.
- Within which session or state history a sequence is comparable, and how an HTTP outcome's state capture relates to the accepted WebSocket history. Arrival order does not supply that relationship.
- What accepted application data proves initial synchronization or resumed synchronization, and which readiness claims remain unknown before that data arrives. Socket liveness is a different fact.
- Whether a specific command was rejected before admission, admitted, completed, partly applied, or remains unobservable, with operation-specific completion evidence. Snapshot freshness alone cannot prove a host effect that produces no state change.

These are unresolved application contracts, not missing transport documentation. The actual deployed Node/browser builds, interruption behavior of this handler, buffer growth under a slow client, and performance costs were not measured. Nothing here selects a provenance format, handshake, acknowledgement mechanism, retry strategy, or architecture.
