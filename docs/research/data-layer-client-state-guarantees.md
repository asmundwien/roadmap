# Data-layer client-state guarantees

Research for [What do React selection, Redux Toolkit, TanStack Query and SSR actually guarantee here?](https://github.com/asmundwien/roadmap/issues/106), under [Rework Roadmap's data layer with clearer models and less code](https://github.com/asmundwien/roadmap/issues/102).

Baseline: `7e70e8975b59aa1b435d444cd9c7ba06c886f8a4`. Sources accessed 2026-10-08. This report establishes facts for the ownership decision. It chooses no framework, library, handshake, retry or timeout policy. No speed claim or need for SSR follows from these documents.

## Scope and versions

The reviewed [web manifest](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/web/package.json) declares React and React DOM `^19.2.8`. Those are dependency ranges, not verified installed versions. It declares neither React Redux, Redux Toolkit, TanStack Query nor the selector-shim package. React documentation is the rolling React 19 reference; selector implementation evidence below is explicitly pinned to React `v19.2.0`. Redux sources are their rolling `current` documentation, with hooks introduced in React Redux 7.1 and hydration support in 8.0. TanStack `/v5/` guide requests redirected to `/latest/` during access. Their retrieved rolling documentation, including generated API pages, is evidence of the documented behavior, not proof of an exact candidate package version. Confirm the selected package version before implementation.

The assignment's application premise is full WebSocket state replacements and one HTTP native-folder-selection query, not independent entity GETs. The reviewed [store](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/web/src/store/roadmap-store.ts#L87-L187) confirms decoded full `ApplicationState` replacements, command responses containing state, and an HTTP query method that returns a result without applying state. The sole native-folder query is an assignment premise, not a caller inventory established by this narrow read.

The [provider](https://github.com/asmundwien/roadmap/blob/7e70e8975b59aa1b435d444cd9c7ba06c886f8a4/apps/web/src/store/roadmap-provider.tsx#L39-L76) subscribes to the whole store snapshot and starts the transport in an effect. The store caches its snapshot between publications, replaces its wrapper on publication, retains domain state on disconnect, and explicitly rejects non-increasing sequences within an epoch and previously retired epochs. These are source observations, not runtime verification or library guarantees.

## Selection and replacement comparison

| Mechanism | Documented contract | Boundary relevant to Roadmap |
| --- | --- | --- |
| React `useSyncExternalStore` | Repeated reads of unchanged state must return the same immutable snapshot. React compares snapshots with `Object.is` and re-renders when they differ. During a Transition it rechecks before DOM changes and restarts as blocking if the snapshot changed. [React reference](https://react.dev/reference/react/useSyncExternalStore#parameters) | The base API has no selector or custom-equality parameter. Selecting after subscribing to the whole wrapper does not narrow the subscription. A selected primitive or stable nested reference can instead be the snapshot, but a freshly allocated derived object on every read violates snapshot caching. This API does not order network messages. |
| React selector helper | The React working group documents `useSyncExternalStoreWithSelector` in the separate `use-sync-external-store/with-selector` package. The pinned implementation memoizes selections for unchanged snapshots and reuses the prior selection when optional `isEqual` says it is equal. [Working-group announcement](https://github.com/reactwg/react-18/discussions/86), [v19.2.0 implementation](https://github.com/facebook/react/blob/v19.2.0/packages/use-sync-external-store/src/useSyncExternalStoreWithSelector.js) | This is not an export or additional overload of React's base hook. A selector helper can avoid store-driven renders for equal selections; it cannot restore object identity across independently decoded replacements unless selection, equality or the data owner provides that behavior. |
| React Redux `useSelector` | Selectors must be pure and may run multiple times. Store updates compare selected results with strict `===` by default, not shallow equality. `shallowEqual`, custom equality and memoized selectors are supported. [Hooks reference](https://react-redux.js.org/api/hooks#equality-comparisons-and-updates) | Returning a new object forces store-driven renders under the default comparison. Equality does not prevent parent-driven renders, and is not a guarantee that selector computation disappears. React Redux is the binding layer; Redux Toolkit itself is not the React subscription API. |
| Redux Toolkit reducers | `createSlice` and `createReducer` use Immer for immutable draft updates. To replace state, return the new value; assigning the reducer's local `state` variable does not replace it. [Immer reducer guide](https://redux-toolkit.js.org/usage/immer-reducers#resetting-and-replacing-state) | Full replacement is supported without decomposing state into entities. Preserving unchanged references while editing an existing draft is not a promise to deep-deduplicate a separately parsed full payload. |
| RTK Query cache | `onCacheEntryAdded` provides lifecycle promises and cache-update tools for streaming. Connection setup, received-message handling and cleanup are application code. Later queries can overwrite the whole entry. `updateQueryData` only patches existing endpoint/argument entries; `upsertQueryData` creates or replaces them. [Streaming guide](https://redux-toolkit.js.org/rtk-query/usage/streaming-updates), [manual cache guide](https://redux-toolkit.js.org/rtk-query/usage/manual-cache-updates) | WebSockets and replacement are supported capabilities, not automatic protocol ownership. The chat example's initial HTTP query and partial patches are examples, not requirements for Roadmap. Cache-entry removal and its connection cleanup are not identical to immediate component unmount. |
| TanStack Query rendering | JSON-compatible query data uses structural sharing by default, retaining equal data or unchanged parts. Hook result wrappers are not stable. Tracked accessed result properties and `select` narrow notifications; object-rest destructuring defeats property tracking. `select` reruns when its function reference or data changes. [Render guide](https://tanstack.com/query/latest/docs/framework/react/guides/render-optimizations) | Unlike reference equality alone, documented structural sharing can retain references across equal JSON replacements. It still performs work and gives no measured advantage for Roadmap's payload sizes. Selection changes observer data, not the authoritative cached value. |

None of these mechanisms suppresses every possible component render. Their equality and notification contracts concern updates from their respective stores or observers, not all React causes of rendering.

## Query defaults are not interaction policy

TanStack's documented browser query defaults treat cached data as stale, refetch stale queries on mount, focus and reconnect, retain inactive queries for five minutes, and retry failed queries three times. Each is configurable. Mutations do **not** retry on error by default; mutation fulfillment can occur in a different order from invocation. [Query defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults), [mutation guide](https://tanstack.com/query/latest/docs/framework/react/guides/mutations#retry).

Calling an application message a `Query` does not establish that it belongs in a library's repeatable-fetch abstraction. Opening a native folder picker is a user interaction. Whether it may be repeated automatically is application policy, even if it does not mutate domain state. The browser query retry default is not a universal server-rendering default or evidence that ambiguous commands are safe to replay.

TanStack `setQueryData` synchronously updates one key and can create it. `setQueriesData` targets existing matching keys and creates none; updates must be immutable. Mutation callbacks can explicitly update or invalidate query data. [QueryClient reference](https://tanstack.com/query/latest/docs/framework/react/reference/classes/QueryClient#setquerydata), [mutation guide](https://tanstack.com/query/latest/docs/framework/react/guides/mutations). These tools permit targeted ownership; they do not require converting the one full-state stream into independent entity caches. Conversely, splitting it would require application rules for updating every affected entry and maintaining cross-entry consistency. No cited cache API substitutes its timestamps or fetch completion order for Roadmap's epoch/sequence admission rule.

## SSR, hydration and async limits

- React calls `getServerSnapshot` during server rendering and initial client hydration. Its data must agree across both; omitting it throws on server rendering. Passing the same function as `getSnapshot` and `getServerSnapshot`, as this provider does, does not itself transfer or synchronize state across processes. [External-store server-rendering reference](https://react.dev/reference/react/useSyncExternalStore#adding-support-for-server-rendering).
- `hydrateRoot` requires the initial client output to match server HTML. Mismatches are bugs, and React does not guarantee patching attribute differences. A client-only root should use `createRoot`, not `hydrateRoot`. [Hydration reference](https://react.dev/reference/react-dom/client/hydrateRoot#caveats).
- React Redux 8+ documents supplying serialized server state through `Provider.serverState` for the initial hydration render. TanStack documents request-isolated query clients and dehydrated data used by both server and client; a process-global SSR cache risks exposing one user's data to another. These are conditional SSR obligations, not reasons to adopt SSR. [Redux Provider](https://react-redux.js.org/api/provider#react-18-ssr-usage), [TanStack SSR guide](https://tanstack.com/query/latest/docs/framework/react/guides/ssr).
- React Server Components execute in an environment separate from the client app and SSR server; their output can optionally be SSR-rendered. They support async components, but async Client Components are unsupported. Interactive state belongs in Client Components; the documented client example reads a server-created promise with `use`. React 19 Server Components are stable, but bundler/framework implementation APIs may break between minor releases. [Server Components reference](https://react.dev/reference/rsc/server-components). Async server rendering is not a browser subscription or a replacement for a live WebSocket owner.

## Facts still needed for the ownership decision

External documentation cannot settle these application-policy or measurement questions:

- Which owner must keep the full authoritative state, transport liveness and command activity, and how long must that owner survive navigation or absence of subscribers?
- Which views need narrow subscriptions, and which object references or derived values should count as unchanged after a replacement? Payload sizes, update rates, selector costs and render costs remain unmeasured.
- How should concurrent folder-selection interactions behave? Which failures mean rejection versus unknown completion, and which operations, if any, are safe to replay? Library defaults do not answer this.
- Must caches remain coherent across multiple keys, or should the whole state remain one atomic replacement? How must epoch changes, stale command responses and disconnected retained state appear to consumers?
- Is server-rendered initial content a product requirement? If so, which state is safe to serialize, how is it request-isolated, and how will server HTML and hydration data agree before live updates start?

The baseline source already contains some answers in implementation. Whether those are required capabilities or incidental policies belongs to the reviewed execution map and its human-owned decisions. This report neither changes them nor resolves a human decision ticket. No commands, tests, builds, formatters or runtime checks were run.
