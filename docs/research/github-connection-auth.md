# Research: GitHub authorization and event delivery

Resolves [Choose GitHub authorization and event delivery](https://github.com/asmundwien/roadmap/issues/41). Researched against current GitHub.com documentation on 2026-08-21.

## Verdict up front

Use one maintainer-owned, public GitHub App for the GitHub Integration. Give it only **Issues: read-only** and **Metadata: read-only** repository permissions, and no account, organization, or write permissions. Enable device flow and expiring user access tokens. Keep webhooks inactive.

Each GitHub Connection should hold a GitHub App user access token obtained through device flow. A Connection represents one authenticated GitHub identity. The same token can see every installation and repository that both that user and the App can access, so installations are access partitions inside a Connection, not Connections themselves. GitHub defines this access as the intersection of the user's access, the App's permissions, and the repositories selected for its installations ([user access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app#about-user-access-tokens)).

Do not use an OAuth App, an installation access token, or either kind of PAT as the steady-state credential. GitHub itself prefers GitHub Apps because they have fine-grained permissions, repository selection, short-lived tokens, and centralized webhooks ([GitHub Apps compared with OAuth Apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps#about-github-apps-and-oauth-apps)). The current PAT configuration is an acceptable bootstrap for the existing single account, but it has no interactive grant or refresh lifecycle and does not model multiple Connections.

Do not keep Smee. GitHub says, without qualification, "Never use Smee for an application in production, because Smee channels are not authenticated or secure" ([webhook URL guidance](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/using-webhooks-with-github-apps#choosing-a-webhook-url-for-development-and-testing)). Roadmap is local, but it handles real private issue bodies and credentials. It is not a webhook development sandbox.

Without a hosted Roadmap service, secure GitHub App webhook delivery to arbitrary local processes has no good shape. A shared GitHub App has one webhook URL for every installation, while GitHub requires that URL to name a web server that receives the App's payloads ([GitHub App webhooks](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/using-webhooks-with-github-apps#choosing-a-webhook-url)). A central relay would make Roadmap a hosted service. A per-user Smee channel is insecure. Asking every user to register an App and operate a tunnel defeats interactive Connection setup. The default event path should therefore be reconciliation over authenticated GraphQL, paced in tens of seconds while Roadmap is active and stretched by the Adapter's rate-limit valve. This gives bounded staleness without adding a public service.

## Tracked starting point

The tracked configuration is one server-side `ROADMAP_GITHUB_TOKEN` plus one `ROADMAP_GITHUB_USER`, with optional `ROADMAP_SMEE_URL` and `ROADMAP_WEBHOOK_SECRET` values ([`.env.example`](../../.env.example)). The token drives discovery and GraphQL reads. The user name bounds search. Smee forwards one GitHub App webhook to the local server, and missing relay settings degrade to polling ([server configuration](../../apps/server/src/config.ts)). The server currently reconciles every five minutes and after relay reconnects ([server startup](../../apps/server/src/main.ts)).

That design did the right first security step by keeping the PAT out of the browser, but the configuration tuple is not a Connection model. It supports one identity, leaves credential creation and expiry to the user, stores the credential in a plaintext environment file, and couples timely updates to an insecure relay. The recommendation below replaces the whole tuple rather than layering interactive authorization over it.

## Recommended App registration

Register one public GitHub App owned by the Roadmap maintainer or a stable maintainer organization. Public here means "installable on any account", not access to public data only. GitHub's registration form calls this setting **Any account** ([registration settings](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app#registering-a-github-app)).

Set it as follows:

| Setting | Value | Reason |
| --- | --- | --- |
| Repository permissions | `Issues: read-only` | This permission covers issue, sub-issue, and dependency reads. GitHub's REST permission matrix lists both `GET .../sub_issues` and `GET .../dependencies/blocked_by` under read-level Issues permission, for both user and installation tokens ([permission matrix](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps#repository-permissions-for-issues)). |
| Repository metadata | `Metadata: read-only` | Keep repository identity available for installation listings and GraphQL repository objects. Do not add Contents. The issue query does not read Git objects or repository files. GitHub automatically restores Metadata to read-only whenever an App requests a permission that requires repository access ([permission matrix](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps#metadata)). |
| Account permissions | None | A Connection only needs the authenticated identity and the repositories exposed by installations. `GET /user/installations` and its repository listing are defined for a GitHub App user access token ([installation listing](https://docs.github.com/en/rest/apps/installations#list-app-installations-accessible-to-the-user-access-token)). |
| Organization permissions | None | Organization membership, hooks, and administration are not part of Project registration or map reads. |
| Device flow | Enabled | The device grant uses the client ID and does not require a callback URL or client secret ([device flow request](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app#using-the-device-flow-to-generate-a-user-access-token)). |
| Expire user authorization tokens | Enabled | This is the registration default and GitHub strongly recommends keeping it enabled ([registration settings](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app#registering-a-github-app)). |
| Request OAuth on installation | Disabled | Authorization and installation are separate. Roadmap drives authorization itself and discovers installations afterward. GitHub allows either operation without the other ([installation versus authorization](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party#difference-between-installation-and-authorization)). |
| Callback URL and setup URL | Empty | Device flow ignores callback configuration, and installation discovery does not need to trust a setup redirect ([registration settings](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app#registering-a-github-app), [setup URL warning](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-setup-url)). |
| Webhooks | Inactive | There is no trusted, durable HTTPS receiver in the local-only architecture. |
| Installation scope | Any account | One App can be installed on a personal account and multiple organizations, and the same App can be installed on multiple accounts ([installation model](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party#about-installing-github-apps)). |

Do not request `Contents`, `Pull requests`, `Members`, `Administration`, `Webhooks`, or any write permission. The GraphQL operation stays a query, and GitHub enforces the permission ceiling even if Roadmap has a bug. GitHub Apps have no permissions by default and GitHub tells App authors to request the minimum needed ([permission model](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app#about-github-app-permissions)).

The existing GraphQL map query remains valid. `Issue.subIssues`, `Issue.subIssuesSummary`, `Issue.blockedBy`, labels, assignees, state, title, body, and repository identity are issue reads in the published [`Issue` object](https://docs.github.com/en/graphql/reference/objects#issue). No issue mutation is needed. The live query and its measured rate cost are recorded in [reading wayfinder primitives from the browser](./github-api-primitives.md#3-blocked-by-edges--the-whole-map-without-one-request-per-ticket).

## Connection and Project registration flow

1. The user chooses **Add GitHub Connection**. The server requests a device code with the shipped App client ID. It displays the returned user code, opens GitHub's verification URL, and polls no faster than GitHub's returned interval. GitHub's device codes expire after 15 minutes, and polling too fast produces `slow_down` and increases the interval ([device flow protocol](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app#using-the-device-flow-to-generate-a-user-access-token)).
2. After authorization, the server calls `GET /user` and records the stable GitHub user ID and current login as non-secret Connection metadata. Revalidating identity after each authorization prevents data from being attached to the wrong signed-in account; GitHub tells App authors to use the durable user ID rather than a changeable login ([GitHub App identity guidance](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app#use-the-durable-unique-id-to-store-the-user)).
3. The server calls `GET /user/installations`. If the user has not installed the App where the desired repository lives, Roadmap opens `https://github.com/apps/APP-SLUG/installations/new`. The user chooses a personal account or organization, then **Only select repositories**. GitHub reserves that repository choice for the installer and may require an organization owner to approve it ([installation requirements and steps](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party#installing-a-github-app)).
4. Roadmap polls `GET /user/installations` and `GET /user/installations/{installation_id}/repositories` after the browser returns. No callback is required. These endpoints list only installations and repositories that the user access token may access, and include the installation's `all` or `selected` repository-selection mode ([installation endpoints](https://docs.github.com/en/rest/apps/installations#list-repositories-accessible-to-the-user-access-token)).
5. A Project registration is created from a repository exposed by one of those installations and is tied to the Connection that authorized the read. Project registration replaces `ROADMAP_GITHUB_USER` discovery as the source of ownership. The GitHub Adapter fetches only registered projects for that Connection.
6. Adding another GitHub account repeats device authorization. The user must make sure the intended account is active on GitHub's device page. Roadmap detects accidental reuse by comparing the returned stable user ID and refuses a duplicate Connection rather than mixing credentials.

One Connection can cover a personal installation and any number of organization installations visible to that identity. Do not create a Connection per installation. Conversely, never share a token between two GitHub identities. A Project registration should retain its Connection ID and stable repository identity so two accounts with access to the same repository remain explicit rather than being deduplicated by owner/name alone.

Repository selection is changed on GitHub's installation settings page. A later reconciliation of the installation lists must treat added repositories as candidates for new Project registrations and removed repositories as unavailable. It must not silently delete an existing Project registration.

## Credential and token lifecycle

The server, never the browser, owns credentials. GitHub says access and refresh tokens must be kept secure ([user token security](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app#about-user-access-tokens)). Store each Connection's `ghu_` access token, `ghr_` refresh token, and expiries together as one secret record in macOS Keychain, keyed by an opaque Connection ID, so rotation cannot persist half a token pair. Apple describes Keychain as storage for passwords and login tokens, with AES-256-GCM encryption and process access enforced by `securityd` ([Apple Keychain protection](https://support.apple.com/guide/security/keychain-data-protection-secb0694df1a/web)). Keep only non-secret identity, installation, status, and expiry metadata in Roadmap's configuration.

Do not put GitHub credentials in `.env.local`, browser storage, URLs, logs, snapshots, or server-to-browser messages. The current `.env.local` at least keeps the PAT server-side and gitignored, but it is plaintext and supports only one `ROADMAP_GITHUB_TOKEN` plus one `ROADMAP_GITHUB_USER`. The App client ID and App slug are identifiers, not bearer credentials; the device exchange needs no client secret ([device flow parameters](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app#using-the-device-flow-to-generate-a-user-access-token)).

Refresh rules:

1. Persist the access token, refresh token, and their absolute expiries immediately after device authorization.
2. Serialize refresh per Connection and refresh before the 8-hour access-token deadline. A refresh request created from device flow needs `client_id`, `grant_type=refresh_token`, and the refresh token; it does not need a client secret ([refresh request](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens#refreshing-a-user-access-token-with-a-refresh-token)).
3. Replace the single Keychain credential record with the returned pair. GitHub invalidates the old access token and old refresh token as soon as a refresh token is used ([rotation semantics](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens#about-user-access-tokens-that-expire)). A crash between refresh and persistence would otherwise force reauthorization.
4. If the refresh token reaches its 6-month expiry, or GitHub returns `bad_refresh_token`, run device authorization again. GitHub documents reauthorization as the recovery path ([refresh failure](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app#bad-refresh-token)). Preserve the Connection identity and Project registrations while showing that authorization is required.
5. On `401 Bad Credentials`, stop API calls for that Connection and require authorization. GitHub returns 401 after a user revokes a GitHub App authorization ([revocation behavior](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app#about-user-access-tokens)).

Removing a Connection deletes its Keychain items and its local metadata through the normal dependency-safe Connection removal flow. That removes Roadmap's local access but does not uninstall or deauthorize the GitHub App. Installation and authorization are independent GitHub grants ([installation versus authorization](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party#difference-between-installation-and-authorization)). Offer links to GitHub's App authorization and installation settings when the user also wants remote revocation. GitHub revokes all associated tokens when the user revokes authorization, and expired or revoked tokens cannot be restored ([token expiration and revocation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation#token-revoked-by-the-user)).

## Event delivery and reconciliation

### Default path

The default path is authoritative polling, not webhook replay:

```text
GitHub change
  -> Connection reconciliation becomes due
  -> GitHub Adapter refreshes the registered project's GraphQL snapshot
  -> Adapter compares and publishes its whole slice
  -> source-blind change feed derives domain events
```

Run a prompt reconcile when Roadmap starts, after authorization or token refresh, after installation/repository selection, on manual refresh, and on a short active cadence. Keep the existing rate-limit valve inside the GitHub Adapter. GitHub user access tokens use the user's rate limit, and GraphQL exposes cost and remaining budget for pacing ([GitHub App rate limits](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/rate-limits-for-github-apps#user-access-token-requests), [GraphQL rate limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)). The current query has already been measured at a few points per map, making an active cadence in tens of seconds practical for Roadmap's local scale ([live measurement](./github-api-primitives.md#3-blocked-by-edges--the-whole-map-without-one-request-per-ticket)). Stretch the cadence when the Connection is rate-limited, offline, or not being viewed.

Reconcile installation membership less often than project data, and immediately after a repository access error. A removed repository, uninstalled or suspended installation, renamed repository, revoked user authorization, or expired refresh token must make only the affected Connection or Project registration unavailable. Keep its last good slice and registration until the user repairs or removes it.

### Why Smee leaves

Smee is explicitly a development and testing service whose channels are unauthenticated and insecure ([GitHub's Smee warning](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/using-webhooks-with-github-apps#choosing-a-webhook-url-for-development-and-testing)). That alone disqualifies it for private issues.

End-to-end signature validation is non-negotiable for a real webhook receiver. GitHub signs the payload contents in `X-Hub-Signature-256` and says proxies must not modify payloads or headers before verification ([validating deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries)). The current environment describes verification after a forwarding service as "best-effort". That is not a security boundary.

Webhooks would not eliminate reconciliation anyway. GitHub tells receivers to respond within 10 seconds, deduplicate with `X-GitHub-Delivery`, and redeliver missed deliveries after downtime ([webhook best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)). A laptop process is routinely down. Polling is the only automatic way for this local architecture to close those gaps.

### Event path if a trusted receiver is ever adopted

A future event receiver is acceptable only if it is authenticated, preserves the exact request body and headers for HMAC validation, durably queues deliveries while Roadmap is offline, and routes each installation to its Connection without exposing one user's payload to another. That is a hosted Roadmap component, not a Smee replacement hidden inside the local app.

With such a receiver, subscribe to exactly:

- `issues` for state, title/body edits, labels, assignees, deletion, and transfer;
- `sub_issues` for parent/sub-issue additions and removals;
- `issue_dependencies` for blocking and blocked-by additions and removals;
- the mandatory `installation`, `installation_repositories`, and `github_app_authorization` lifecycle events.

All three issue event families require only read-level Issues permission, and GitHub documents their action sets separately ([`issues`](https://docs.github.com/en/webhooks/webhook-events-and-payloads#issues), [`sub_issues`](https://docs.github.com/en/webhooks/webhook-events-and-payloads#sub_issues), [`issue_dependencies`](https://docs.github.com/en/webhooks/webhook-events-and-payloads#issue_dependencies)). GitHub Apps receive installation and installation-repository changes by default and cannot unsubscribe; authorization revocation is also mandatory ([installation lifecycle events](https://docs.github.com/en/webhooks/webhook-events-and-payloads#installation), [authorization revocation event](https://docs.github.com/en/webhooks/webhook-events-and-payloads#github_app_authorization)).

Treat every delivery as an invalidation hint. Validate HMAC against the untouched body, deduplicate by delivery ID, acknowledge quickly, locate the affected Connection and Project registration from the installation and repository IDs, then fetch authoritative GraphQL state. Keep the periodic reconciler. Never apply issue payloads directly to Roadmap state.

## Automation and setup boundary

### Maintainer provisioning

Roadmap needs one externally registered GitHub App before it can ship a client ID and installation URL. GitHub App registration is a GitHub settings action, and enabling device flow is an explicit registration option ([registration procedure](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app#registering-a-github-app)). This one-time release-maintainer task warrants a repeatable `/wizard` because a person must own the App, choose **Any account**, verify the exact permissions above, enable device flow and expiry, and leave webhooks inactive. The wizard should record the non-secret client ID and App slug, not a private key or client secret.

A GitHub App manifest can preconfigure permissions, events, webhook URL, visibility, and return a private key, client secret, webhook secret, and App ID ([manifest capabilities](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest#about-github-app-manifests)). It is the wrong automation boundary here. It creates an App owned by each person running the flow, does not remove the separate device-flow setting, and would multiply App ownership and webhook configuration across Connections. Use one maintained App instead.

### End-user setup

End users should not run `/wizard`. Add Connection is a product flow that can automate device-code creation, browser opening, token polling, identity validation, installation discovery, repository listing, and health checks. The two unavoidable GitHub pages are consent and installation repository selection. GitHub deliberately reserves both decisions for the user or organization administrator ([authorization and installation model](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party#difference-between-installation-and-authorization)). Roadmap should deep-link to those pages and resume by polling GitHub, rather than asking users to transcribe tokens or edit environment variables.

## Risks and rejected compromises

- **No push while the process is idle.** Polling produces bounded rather than immediate freshness. This is the honest cost of staying local without an insecure relay or hosted receiver. Use a short active cadence and immediate reconciliation on user actions.
- **Organization policy can block installation.** Organization owners may restrict installations, and a repository administrator may have to request approval ([installation requirements](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party#requirements-to-install-a-github-app)). Roadmap should report "installation approval required", not fall back to a broader PAT.
- **Authorization and installation can drift independently.** A valid user token may lose a repository because the installation changed, and an installed App may have no valid user authorization. Reconcile both lists and expose the actual missing grant.
- **Refresh rotation has a crash edge.** GitHub invalidates the old pair during refresh. Serialize and atomically persist the replacement pair, or reauthorization becomes the only recovery.
- **A shared public App has a shared device-flow quota.** GitHub rate-limits device-code submissions and requires clients to honor the polling interval ([device-flow limits](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#rate-limits-for-the-device-flow)). This is acceptable for a single-user local tool but should be visible as an authorization error rather than retried aggressively.
- **Do not add write permission to regain webhooks.** OAuth repository hooks require write scope, while GitHub App issue events need only Issues read. The blocker is safe local delivery, not GitHub event permission.
- **Do not ship the App private key.** A private key can mint the App JWT used to request installation tokens, so distributing it would expose every installation that key controls ([installation token flow](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app#generating-an-installation-access-token)). Device-flow user tokens need only the public client ID.
- **A shared public App requires trust in its owner.** The maintainer controls the App registration and must never distribute its private key; GitHub warns that a private key grants access to every account where the App is installed ([private-key security](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app#private-keys)). Users should see the App owner and exact read-only permissions before installation.
- **Do not retain PAT as a fallback.** A fallback becomes a second credential lifecycle and invites users to bypass organization installation policy. Reauthorize the existing account through the GitHub App and remove the old PAT configuration during the product cutover.
